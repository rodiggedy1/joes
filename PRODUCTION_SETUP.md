## 1. Add a private MySQL database in Railway

Open your existing Railway project for Good Joe. On its project canvas, select **+ New**, choose **Database**, then choose **MySQL**. Leave the database private; the Good Joe web service can reach it over Railway’s internal network, so there is no reason to expose the database to the public internet.

When it has finished provisioning, note the database service’s exact displayed name. Railway’s default is commonly `MySQL`, but use the name shown in your project. Railway makes `MYSQL_URL` and the individual MySQL connection variables available from the database service. [1]

## 2. Add the first two service secrets

Open the existing Good Joe web service in Railway, then open **Variables**. Add the following variables exactly. These are server-side values; they must not be placed in client code or committed to GitHub.

| Variable | Value to enter | Why it is needed |
|---|---|---|
| `DATABASE_URL` | `${{MySQL.MYSQL_URL}}` | Connects the Good Joe API to the private MySQL service. Replace `MySQL` only if your database service uses another name. |
| `JWT_SECRET` | A new random secret generated by your password manager, at least 32 random bytes / 64 random characters | Signs the private customer session cookie after a booking. Do not reuse another password or send this value to me. |

Do **not** add the older Manus OAuth variables (`VITE_APP_ID`, `OAUTH_SERVER_URL`, or `VITE_OAUTH_PORTAL_URL`) for public customers. The production customer flow is being changed to Good Joe’s own booking-session and SMS recovery model.

## 3. Prepare Quo (formerly OpenPhone) for SMS recovery

Good Joe will not require a text before the customer sees their account. SMS is used later to recover the account on a new device and to protect sensitive account changes.

In Quo, open **Workspace Settings → API**, then generate a new key labelled `good-joe-production`. Quo says this requires a workspace Owner or Admin account. Store the key only in Railway; do not paste it into chat or commit it to GitHub. Quo’s API uses the raw key in the `Authorization` header, not a Bearer token. [2]

Before attempting any real US customer message, confirm that your Quo workspace has completed US carrier registration and has API messaging credits. Quo documents both as requirements for programmatic SMS. [2] [3]

Back in the Good Joe Railway web-service **Variables** panel, add these values:

| Variable | Value to enter | Why it is needed |
|---|---|---|
| `QUO_API_KEY` | The production key you generated in Quo | Allows the server to request SMS delivery. |
| `QUO_FROM_NUMBER` | Your actual Good Joe Quo number in E.164 form, for example `+14155550123` | The sender used for account-recovery messages. Quo accepts an E.164 sender number or its phone-number ID. [3] |
| `STAFF_ADMIN_PHONES` | A comma-separated allowlist of the mobile numbers that may use Operations, in E.164 form | Limits staff access to explicitly approved staff mobile numbers after SMS verification. Do not include customer numbers. |

## SMS recovery security standard

Good Joe’s SMS recovery will use short-lived, single-use verification codes generated with cryptographically secure randomness. Code values will be stored only as short-lived hashes; they will never be logged or retained as plaintext. The verification service will enforce strict per-phone and per-network send limits, a small verification-attempt limit, a new code on each resend, and automatic invalidation immediately after a successful verification. These controls follow OWASP’s OTP handling guidance. [4]

The customer’s booked-device session will remain frictionless, while a new device, account recovery, sensitive profile change, or Operations access will require the verified mobile factor. This is risk-based step-up authentication: NIST describes authentication as establishing that the claimant controls an authenticator bound to the account, while OWASP advises higher assurance for privileged actions. [4] [5]

## What this gives Good Joe

| Customer moment | Production behavior |
|---|---|
| Completes booking | The booking saves and opens a private account immediately, without a password or text-code hurdle. |
| Returns on the same device | Their signed session opens their account directly. |
| Changes device or needs recovery | They enter their mobile number and verify a time-limited SMS code. |
| Visits Operations | They must verify an allowlisted staff mobile number; customer sessions can never call Operations APIs. |
